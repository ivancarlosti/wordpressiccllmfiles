# Translations and RTL

The plugin loads its own translation catalogs from `languages/` and renders right-to-left for
Arabic. This document describes the shipped locales, how the catalogs are loaded, and how to
update them.

## Supported locales

| Documented code | WordPress locale | Catalog (`.po` / `.mo`) | Direction |
|---|---|---|---|
| `en-US` (fallback) | `en_US` (and every other `en_*`) | `icc-gg-llm-files-generator-en_US` | LTR |
| `pt-BR` | `pt_BR` | `icc-gg-llm-files-generator-pt_BR` | LTR |
| `es-MX` | `es_MX` | `icc-gg-llm-files-generator-es_MX` | LTR |
| `fr-FR` | `fr_FR` | `icc-gg-llm-files-generator-fr_FR` | LTR |
| `zh-CN` | `zh_CN` | `icc-gg-llm-files-generator-zh_CN` | LTR |
| `hi-IN` | `hi_IN` | `icc-gg-llm-files-generator-hi_IN` | LTR |
| `ar-SA` | `ar` (and every other `ar_*`) | `icc-gg-llm-files-generator-ar` | **RTL** |

`en_US` is an identity catalog: every `msgstr` equals its `msgid`. It exists so English is an
explicit fallback target and so a locale without a catalog keeps the source strings instead of
falling through to an unrelated one.

## Files

```
languages/
├── icc-gg-llm-files-generator.pot           source strings (template, not shipped to WordPress)
├── icc-gg-llm-files-generator-en_US.po/.mo
├── icc-gg-llm-files-generator-pt_BR.po/.mo
├── icc-gg-llm-files-generator-es_MX.po/.mo
├── icc-gg-llm-files-generator-fr_FR.po/.mo
├── icc-gg-llm-files-generator-zh_CN.po/.mo
├── icc-gg-llm-files-generator-hi_IN.po/.mo
└── icc-gg-llm-files-generator-ar.po/.mo
```

Only the `.mo` files are read at runtime; the `.po` files are the editable source, and the `.pot`
template is the reference for translators. All three are committed.

## How the catalogs are loaded

1. The plugin header declares both the text domain and the folder:

   ```php
   * Text Domain:       icc-gg-llm-files-generator
   * Domain Path:       /languages
   ```

   `Domain Path` is what makes WordPress look for a catalog inside the plugin folder.

2. `icc_gg_llm_files_generator_load_textdomain()` runs on `plugins_loaded` priority `5` and calls
   `load_plugin_textdomain()` with the path derived from the plugin basename:

   ```php
   load_plugin_textdomain(
       'icc-gg-llm-files-generator',
       false,
       dirname( ICC_GG_LLM_FILES_GENERATOR_BASENAME ) . '/languages'
   );
   ```

   Using the basename instead of a hard-coded slug keeps both layouts working: a git clone lands in
   `wp-content/plugins/wordpressiccllmfiles/`, a release install in
   `wp-content/plugins/icc-gg-llm-files-generator/`.

   WordPress only auto-loads language packs installed in `wp-content/languages/plugins`, which is
   why the bundled catalog has to be loaded explicitly. Language packs still win when the site
   installs one: `load_plugin_textdomain()` prefers the global directory.

3. `icc_gg_llm_files_generator_plugin_locale()` (filter `plugin_locale`) maps the requested locale
   to a shipped catalog:

   | Requested | Returns |
   |---|---|
   | `pt_BR`, `pt-BR`, `es_MX`, `fr_FR`, `zh_CN`, `hi_IN`, `en_US` | the same locale, normalised to underscores |
   | any other `en_*` (`en_GB`, `en_CA`, `en`) | `en_US` |
   | any `ar*` (`ar`, `ar_SA`, `ar_EG`) | `ar` |
   | anything else | unchanged (English source strings) |

   The filter is global, so it returns `$locale` immediately for any other text domain.

## Right-to-left support

`is_rtl()` follows the **site** locale, which is wrong in the admin: a user whose profile language
is Arabic on an English site gets an LTR admin. `icc_gg_llm_files_generator_is_rtl_locale()` instead
reads the locale that actually drives translations (`determine_locale()`, falling back to
`get_locale()` before WordPress 4.7) and matches `ar`, `fa`, `he`, `ur`, `ckb`, `dv`, `ps`, `sd`,
`ug`, `yi`.

Three filters/behaviours follow from it:

- `language_attributes` appends `dir="rtl"` when core did not already set a direction.
- `admin_body_class` adds the `rtl` class so the admin stylesheet that ships with WordPress applies.
- The settings page enqueues `css/styles-admin-rtl.css` after `css/styles-admin.css`, which mirrors
  the summary block's alignment and moves the left accent border to the right side.

RTL detection is independent of the catalog: an `ar_EG` site renders RTL even though it uses the
`ar` catalog, and any other RTL language the plugin has no catalog for still renders RTL in English.

## Using a translated locale

Nothing has to be configured: install the plugin and set **Settings → General → Site Language**, or
**Users → Profile → Language** for a single account, to one of the supported locales.

```bash
wp option update WPLANG pt_BR
wp user meta update admin locale ar
```

## Updating the catalogs

### Source string changed or added

1. Re-extract the template and refresh every catalog:

   ```bash
   xgettext \
     --language=PHP --from-code=UTF-8 --add-comments=translators: \
     --keyword=__ --keyword=_e --keyword=_x:1,2c --keyword=_n:1,2 \
     --keyword=esc_html__ --keyword=esc_attr__ --keyword=esc_html_e --keyword=esc_attr_e \
     -o /tmp/icc-gg-llm-files-generator.pot \
     icc-gg-llm-files-generator.php includes/*.php
   ```

2. Replace the body of `languages/icc-gg-llm-files-generator.pot` with the new strings, keeping its
   header (charset, `X-Domain`, bug address).
3. Merge the template into each catalog and translate the new entries:

   ```bash
   for po in languages/*.po; do msgmerge --update --backup=none "$po" \
     languages/icc-gg-llm-files-generator.pot; done
   ```

4. Fill in the new `msgstr` values, then rebuild and validate:

   ```bash
   sh tests/build-translations.sh
   ```

`msgfmt --statistics` must report every entry as translated — the script fails on `fuzzy`,
`untranslated` or `obsolete` messages and when a catalog is missing an entry that the template has.

### Adding a locale

1. Create `languages/icc-gg-llm-files-generator-<locale>.po` (copy an existing catalog, set
   `Language:` and the correct `Plural-Forms:`).
2. Translate every entry, then run `sh tests/build-translations.sh` to produce the `.mo`.
3. Allow the locale in `icc_gg_llm_files_generator_plugin_locale()` if it is not already reachable,
   and add it to the table above.
4. For a right-to-left language, extend the pattern in `icc_gg_llm_files_generator_is_rtl_locale()`
   and add any mirroring the settings page needs to `css/styles-admin-rtl.css`.

### Rules for translators

- Keep every placeholder exactly as it appears: `%s`, `%1$s`, `%2$d`. `msgfmt --check` rejects a
  translation whose format specifiers do not match the source.
- Never translate the JSON keys `insert` and `remove`, file names (`llms.txt`, `llms-full.txt`),
  option names, URLs or function names — the AI prompt strings and the diff parser depend on them.
  Examples inside a prompt (`- New page: Title (https://example.com/page)`) stay in English.
- Keep HTML tags (`<strong>`, `</strong>`) balanced and in the same order.
- `zh_CN` uses a single plural form (`nplurals=1`), `ar` uses six.

## Verification

```bash
# Lint, layout and catalogs
find . -name '*.php' -not -path './vendor/*' -exec php -l {} \;
sh tests/validate-plugin-layout.sh
sh tests/build-translations.sh --check-pot
```

`--check-pot` re-runs `xgettext` and fails when the committed template no longer matches the source
strings, which is what happens when a string is edited without refreshing `languages/`.

`tests/check-translations.php` parses the compiled `.mo` files directly, so it needs neither
WordPress nor the locales installed on the machine. It runs as part of `build-translations.sh` and
can be called on its own:

```bash
php tests/check-translations.php
```

`tests/check-i18n-bootstrap.php` covers the wiring instead of the strings: it stubs the handful of
WordPress functions the plugin calls while loading, requires the main plugin file and asserts that
`load_plugin_textdomain()` points at this plugin's `languages/` folder, that `plugin_locale` maps
`pt-BR`/`es-MX`/`zh-CN`/`ar_SA`/`en_GB` as documented above, and that `is_rtl_locale()`,
`language_attributes` and `admin_body_class` only change right-to-left output.

```bash
php tests/check-i18n-bootstrap.php
```

Runtime smoke test without WordPress — the compiled catalogs are plain GNU gettext files:

```bash
python3 - <<'PY'
import gettext
for locale in ['pt_BR', 'es_MX', 'fr_FR', 'zh_CN', 'hi_IN', 'ar']:
    with open(f'languages/icc-gg-llm-files-generator-{locale}.mo', 'rb') as handle:
        print(locale, gettext.GNUTranslations(handle).gettext('Settings'))
PY
```

In WordPress, switch the site or profile language and reload **Settings → LLM Files Generator**; for
Arabic the page must be mirrored (`dir="rtl"`, `rtl` body class) and the summary block's accent
border must sit on the right.

## Release packaging

`.github/workflows/build.yml` packages the release with `zip -r … .`, so `languages/` is included
automatically; no workflow change is needed when catalogs are added. The `.dockerignore` keeps
`docs/`, `plans/`, `docker/` and `.github/` out of Docker build contexts only — it does not affect
the ZIP. Verify a release archive with:

```bash
unzip -Z1 icc-gg-llm-files-generator.zip | grep '^icc-gg-llm-files-generator/languages/'
```
